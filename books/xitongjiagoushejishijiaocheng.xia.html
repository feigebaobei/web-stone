信息系统架构基本概念及发展

对于大规模的复杂系统来说，总体的系统结构设计比计算算法和数据结构更重要。 信息系统的架构本质上存在 2 个层次：

  • 概念层次
  • 物理层次 信息系统架构是关于软件系统的结构、行为和属性的高级抽象。 企业架构框架是 TOGAF The Open Group Archietecture Framework, open group 架构框架 几乎所有领域都能够和信息技术相结合 构成企业信息化项目。 包括：
  • 信息系统架构描述语言
  • 信息系统架构的描述与表示
  • 信息系统架构的分析与验证
  • 基于架构的软件维护与演化
  • 信息系统架构的可靠性 关于其定义中的说明：
  • 架构是系统的抽象
  • 架构由多个结构组成
  • 任何软件都存在架构
  • 元素及其行为的集合构成架构的内容
  • 架构具有“基础”性。
    • 通常涉及解决各类关键重复问题的能用方案
    • 系统设计中影响深远的各项重要决策
  • 架构隐含有“决策”
    • 架构设计师根据功能与非功能需求进行设计与决策的结果 影响架构的因素：
  • 软件系统的干系人对其有不同的要求
  • 开发组织有不同的人员知识结构
  • 架构设计师的素质与经验
  • 当前的技术环境 这些因素也会影响架构。

信息系统架构

信息系统设计的一个核心问题是能否使用重复的信息系统架构模式，即能否达到架构级别的软件重用。即能否在不同的软件系统中使用同一架构。 信息系统架构风格是描述某一特定应用领域中系统组织方式的惯用模式。 约束指出系统是如何将构件和连接件组合起来的。 根据特定项目的具体特点选择或设计特写的架构风格：

  • 数据流风格：批处理序列，管道、过滤器
  • 调用、返回风格：主程序、子程序，面向对象风格，层次结构
  • 独立构件风格：进程通信，事件系统
  • 虚拟机风格：解释器，基于规则的系统
  • 仓库风格：数据库系统，超文本系统，黑板系统 信息系统架构分类：
  1. 信息系统物理结构
    • 在空间上的拓扑关系
    • 集中式结构
      • 物理资源有空间上集中配置
      • 优点
        • 资源集中
        • 便于管理
        • 资源利用率较高
      • 缺点
        • 维护、管理比较困难
        • 不利于用户发挥在信息系统建设过程中的积极性与主动性
        • 过于集中会造成系统的脆弱
    • 分布式结构
      • 通过计算机网络把不同地点的计算机硬件、软件、数据等资源联系在一起，实现不同地点的资源共享。
      • 分布式结构已经成为信息系统的主流模式。
      • 优点
        • 按需配置资源
        • 安全性好。一个结点出现故障不会导致整个系统停止运作
      • 缺点
        • 系统管理的标准不统一。
      • 分类
        • 一般分布式
        • 客户机、服务器
  2. 信息系统的逻辑结构
    • 信息系统的逻辑结构是其功能综合体和概念性框架
    • 一个完整的信息系统支持组织的各种功能子系统
    • 将信息系统按职能划分成一个个职能子系统，然后逐个研制和开发。
    • 强调各子系统之间的协调一致性和整体性。
    • 横向综合
    • 纵向综合
    • 纵横综合

战备系统

企业中与战略制定、高层决策有关的管理活动和计算机辅助系统。 组成：

  • 以计算机为基础的高层决策支持系统。
  • 企业的战略规划体系。 意义
  • 信息系统对企业高层管理者的决策支持能力
  • 企业战略规划对信息系统建设的影响和要求
业务系统

完成一定业务功能的各部分组成的系统。 作用：

  • 对企业现有业务系统、业务过程和业务活动进行建模。
  • 在企业战略的指导下，采用业务流程重组的原理和方法进行业务过程优化重组。
  • 并对重组后的业务领域、业务过程和业务活动进行建模，从而确定出相对稳定的数据
  • 以此相对稳定的数据为基础，进行企业应用系统的开发和信息基础设施的建设
应用系统

即应用软件系统。

企业信息基础设施 Enterprises Information Infrastructure EII

可分成 3 部分：

  • 技术基础设施由计算机、网络、系统软件、支持性软件、数据交换协议等组成。
  • 信息资源设施由数据与信息本身、数据交换的形式与标准、信息处理方法等组成。
  • 管理基础设施指企业中信息系统部门的组织结构、信息资源设施管理人员的分工、企业信息基础设施的管理方法与规章制度等。

ADM 架构开发方法

The Open Group Architecture Framework TOGAF 是一种开放式企业架构框架标准。由国际标准权威组织 The Open Group 制定。 它是基于一个迭代(Iterative)的过程模型，支持最佳实践和一套可重用的现有架构资产。 功能：

  • 确保从关键利益相关方到团队成员的所有用户都使用相同的语言。
  • 避免被“锁定”到企业架构的专有解决方案。
  • 节省时间和金钱，更有效地利用资源。、
  • 实现可观的投资回报。 TOGRF 的 6 个组件：
  • 架构开发方法 Architecture Development Method ADM. 即一种开发企业架构的分步方法。
  • ADM 指南和技术 可用于应用 ADM 的指南和技术
  • 架构内容构架
  • 企业连续体和工具
  • 参考模型：技术参考模型、集成信息基础设施参考模型
  • 架构能力框架 其框架的核心思想：
  • 模块化架构
  • 内容框架
  • 扩展指南
  • 架构风格
ADM 架构开发方法

定义开发企业架构所需要执行各个步骤以及它们之间的关系。

ADM 的架构开发阶段

由一组按照架构领域的架构开发顺序而排列成一个环的多阶段所构成。 十个阶段是反复迭代的过程。 每个阶段都需要根据原始业务需求对设计结构进行确认。 3 个级别的迭代概念：

  • 基于 ADM 整体的迭代
  • 多个开发阶段间的迭代
  • 在一个阶段内部的迭代。

预备阶段

  • A. 架构愿景 将启动一次架构开发过程的迭代，设置迭代工作的范围、约束、期望，创建架构愿景、验证业务上下文，创建架构工作说明书并取得大家的一致认可。
  • B. 业务架构 将开发一个支持架构愿景的业务架构。架构愿景中概括的基线和目标业务架构将在此被细化，从而使它们可以作为技术分析的有效输入。
  • C. 信息系统架 确定主要的信息类型和处理这些信息的应用系统。在本阶段有 2 个主要的步骤，数据架构设计和应用架构设计。二者可以依次开发，也可以并行开发。
  • D. 技术架构 完成对系统基础服务设施的设计，定义了架构解决方案的物理实现。
  • E. 机会及解决方案 确定目标架构交付物
  • F. 迁移规划 制订一个详细的实现和迁移计划，完成从基线架构向目标架构的转变。
  • G. 实施治理 实施项目的架构结束，提供项目构建的架构监督，产生一个架构契约。
  • H. 架构变更治理 确保以一种可控制的方式对架构的改变进行管理。
  • 需求管理 是一个动态的过程，完成对企业需求的识别、存储并把它们插入或取出相应的 ADM 阶段。它是 adm 流程的中心。

层次式体系结构概述

软件体系结构不仅指定了系统的组织结构和拓扑结构，并且显示了系统需求和构成系统的元素之间的对应关系。 软件体系结构的影响：

  • 利益相关人员之间交流
  • 系统设计的前期决策
  • 可传递的系统级抽象 层次式体系结构设计是将系统组成一个层次结构，每一层为上层服务，并作为下层客户。 每一层最多蛤影响 2 层。同时只为邻层提供相同的接口，允许每层不同的方法实现。同样为软件重用提供了强大的支持。 每层都有一个功能、角色、职能。 分层构架的特点是关注分离 seperation of concerns

viewmodel 负责 view/model 之间的交互，它是核心。通过 dataBinding 实现 view、model 之间的双向绑定，其内容包括数据状态处理、数据绑定及数据转换。 viewmodel 是视图模型，是一个专门用于数据转换的控制器，它可以把对象信息转换为视图信息，将命令从视图携带到对象。 viewmodel 是一个观察者，当数据发生变化，viewmodel 能够监听到数据的变化，然后通知对应的视图做更新。 当用户操作视图，viewmodel 也能监听到视图的变化，出通知数据做改动，从面形成数据的双向绑定。 适用于数据驱动的场景，尤其是数据操作特别频繁的场景。

工作流管理联盟 workflow management coalition 将工作流定义为：业务流程的全部或部分自动化，在此过程中，文件、信息或任务按照一定的过程规则流转，实现组织成员间的协调工作以达到业务的整体目标。 它是一种反映业务流程的计算机化的模型。 优点：

工厂模式在数据访问层应用

数据库的访问需要良好的封装性和可维护性。 工厂模式定义一个用于创建对象的接口，让子类决定实例化哪个类。

interface DataAccess {
  DatabaseType: () => DatabaseType
  DbConnection: () => IDbConnection
  Open: () => void
  Close: () => void
  BeginTransaction: () => IDbTransaction
  ExecuteNonQuery: (commandText: string) => number
  ExecuteDataset: (commandText: string) => dataSet
}
// 工厂函数
class DataAccessFactor {
  constructor() {
    this.defaultPersistenceProperty = {}
  }
  CreateDataAccess(pp) {
    switch (pp.databaseType) {
      case DatabaseType.MSSQLServer:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
      case DatabaseType.Oracle:
        dataAccess = new OracleDataAccess(pp.connectionString)
        break;
      case DatabaseType.OleDBSupported:
        dataAccess = new OleDbDataAccess(pp.connectionString)
        break;
      default:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
    }
  }
  static DataAcess() {
    return CreateDataAccess(defaultPersistenceProperty)
  }
}
// 使用
let pp = {...}
let db = DataAccessFactor.DataAccess(pp)
db.Open()
// 操作数据库
db.Close()

事务处理设计

事务是现代数据库的核心概念之一。 ACID 原则：

  • 原子性 atomicity 表示事务执行过程中的任何失败都导致事务所做的任何修改失效。
  • 一致性 consistency 表示当事务执行失败时，所有被该事务影响的数据都恢复到事件执行前的状态。
  • 隔离怀 isolation 表示在事务执行过程中对数据的修改，在事务提交之前对其他事务不可见。
  • 持久性 durability 表示已提交的数据在事务执行失败时，数据的状态都应该正确。 常见的事务：
  • JDBC 事务
  • JTA 事务
  • 容器管理事务

连接对象管理设计

资源池设计模式。为了解决资源频繁分配、释放所造成的问题。把该模式应用到数据库连接管理领域，就是建立一个数据库连接池，提供一套高效的连接分配、使用策略。 运行过程：

  1. 建立静态连接池。（池中的连接是在系统初始化时分配好的，并且不能随意关闭。）
  2. 当请求时，若存在空闲连接，则使用空间连接；否则共享一个合适的连接。

  • 三方软件
  • 处理非功能特性的代码 具备云原生架构的应用可以最大程序利用云服务和提升软件交付能力。

云原生架构原则

云原生架构是一种架构，有若干架构原则作为应用架构的核心架构控制面，通过遵从这些架构原则可以让技术主管和架构师在做技术解决时不会出现大的偏差。

服务化原则
  • 当代码量超出小团队的合作范围时，就有必要进行服务化拆分。
  • 通过服务化架构把不同生命周期的模块分离出来，分别进行业务迭代。
  • 服务化架构以面向接口编程
  • 模块间通过公共功能模块的提取增加软件的复用程序。 分布式环境下的限流降级、熔断隔仓、灰度、反压、零信任安全等，本质是是基于服务流量的控制策略。所以云原生架构强调使用服务化的目的还在于从架构层面抽象化业务模块之间的关系，标准化服务流量的传输，从而帮助业务模块进行基于服务流量的策略控制和治理。
弹性原则

系统的部署规模可以随着业务量的变化而自动伸缩，无须根据事先的容量规划准备固定的硬件和软件资源。

可观测原则
韧性原则

代表了当软件所依赖的软硬件组件出现各种异常时，软件表现出来的抵御能力。 核心目标是提升软件的平均无故障时间（Mean Time Between Failure MTBF） 韧性包括：

  • 异步化能力
  • 重试
  • 限流
  • 降级
  • 熔断
  • 反压 当下游处理能力不足时，向上游施压，以减小数据发送速率。
  • 主从模式
  • 集群模式
  • AZ（同城多可用区）内的高可用
  • 单元化
  • 跨Region容灾
  • 异地多活容灾
所有过程自动化原则
  • 标准化企业内部的软件交付过程
  • 在标准化的基础上进行自动化
零信任原则

默认情况下不应该信任网络内部和外部的任何人、设备、系统，需要基于认证和授权重构访问控制的信任基础。

架构持续演进原则

在整个软件生命周期里面往往需要对架构进行一定范围内的重构。

主要架构模式

服务化架构模式

是云时代构建云原生应用的标准架构模式：

  • 以应用模块为颗粒度划分一个软件。
  • 以接口契约（如idl）定义彼此业务关系
  • 以标准协议（http/grpc）确保彼此的互联互通
  • 结合ddd/tdd/容器化部署提升每个接口的代码质量和迭代速度。 通过服务化架构，把代码模块关系和部署关系进行分离，每个接口可以部署不同数量的实例。
mesh化架构模式

把中间框架从业务进程是分离，让中间件sdk与业务代码进一步解耦，从而使中间件升级对业务进程没有影响，甚至迁移到另外一个平台的中间件也对业务透明。

serverless模式

当业务流量到来（业务事件发生）时，云会启动或调度一个已启动的业务进程进行处理，处理完成后云自动会关闭（调度业务进程），等待下一次触发，也就是把应用的整个运行都委托给云。 不适合情况：

  • 应用有状态
  • 长时间后台运行的密集型计算任务的应用
  • 应用涉及频繁的外部i/o 适合情况
  • 事件驱动的数据计算任务
  • 计算时间短的请求、响应应用
  • 没有复杂互相调用的长周期任务
存储计算分离模式

分布式环境中cap困难主要是针对有状态应用。 c 一致性 a 可用性 p 分区容错性 在云环境中，推荐把各类暂态数据、结构化、非结构化持久数据把采用云服务来保存，从而实现存储计算分离。

分布式事务模式
  • 传统采用XA模式，虽然具备很强的一致性，但是性能差。
  • 基于消息的最终一致性BASE通常有很高的性能，但是通用性有限。
  • TCC模式完全由由应用层来控制事务，事务隔离性可控，也可以做到比较高效；但是对业务侵入性非常强，设计开发维护等成本很高。
  • SAGA模式与TCC模式的优缺点类似但没有try这个阶段，而是每个正向事务都对应一个补偿事务，也是开发维护成本高。
  • 开源项目SEATA的AT模式非常高性能且无代码开发工作量，且可以自动执行回滚操作，同时也存在一些使用场景限制。
可观测架构

包括:

  • Logging
    • 提供多个组织的详细信息跟踪 verbose/debug/warning/error/fatal
    • 由应用的开发者主动提供。
  • Tracing
    • 提供一个请求从前端到后端的完整链路跟踪
    • 对于分布式场景尤其有用
  • Metrics
    • 提供对系统量化的多维度度量
事件驱动架构 event driven architecture EDA

本质是一种应用、组件间的集成架构模式。 事件驱动不仅用于（微）服务解耦，还可用于：

  • 增强服务韧性
    • 服务间是异步集成的。下游服务器的运行状态不影响上游服务器。
  • command query responsibility segregation CQRS
    • 把对服务状态有影响的命令用事件来发起。
    • 对服务状态无影响的命令用同步调用的api接口。
    • 可以用于维护数据变更的一致性。
  • 数据变化通知
  • 构建开放式接口
  • 事件流处理 在iot时代大量传感器产生的数据，不会像人机交互一样需要等待处理结果的返回，天然适合用eda来构建数据处理应用。

典型的云原生架构反模式

（逆设计模式进行）

  • 庞大的单体应用
    • 代码耦合带来的责任不清
    • 模块间接口缺乏治理而带来变更影响扩散。
    • 不同模块间的开发进度和发布时间要求难以协调
    • 一个子模块不稳定导致整个应用都变慢。
    • 扩容时只能整体扩容，不能对达到瓶颈的模块单独扩容。
  • 单体应用“硬拆”为微服务
    • 服务的拆分要求适度，过分服务化拆分会导致新架构与组织能力不匹配。
    • 错误示例
      • 小规模软件的服务拆分
      • 数据依赖
      • 性能降低
  • 缺乏自动化能力的微服务

云原生微服务

微服务发展背景

将帮助应用架构全面升级，让应用天然具有更好的可观测性、可控制性、可容错性。

微服务设计约束
  • 微服务个体约束
    • 所完成的功能在业务域上是相互独立的。
  • 微服务与微服务之间的横向关系
    • 从可发现性和可交互性处理服务间的横向关系。
    • 引入第三方服务注册中心来处理服务的可发现性。
    • 服务间的调用使用与语言无关的远程调用协议。
    • 服务间使用事先约定接口来完成调用。
  • 微服务与数据层之间的纵向约束
    • 提倡数据存储隔离 Data Storage Segregation DSS 原则。即数据是微服务的私有资产。必须通过当前微服务提供的api访问。
    • 读写分离（CQRS）
  • 全局视角下的微服务分布式约束
    • 高效运维整个系统，从技术上要准备全自动化的ci/cd流水线满足对开发效率的访求。
    • 面对复杂系统，全链路、实时、多维度的可观测能力成为标配。为了及时、有效地防范各类运维风险，需要从微服务体系多种事件源汇聚并分析相关数据。

无服务器技术

技术特点

面向特定领域的后端云服务（BaaS） 无服务器技术（serverless）因为屏蔽了服务器的各种运维复杂度，让开发人员可以将更多精力用于业务逻辑设计与实现。

  • 全托管计算服务
  • 能用性
  • 自动弹性伸缩
  • 按量计费
技术关注点
  • 计算资源弹性调度
    • 容错
    • 资源利用率
    • 性能
    • 数据驱动
  • 负载均衡和流控
  • 安全性

服务网络 Service Mesh

技术特点

分布式应用在微服务软件架构上发展起来的新技术。将微服务间的连接、安全、流量控制、可观测等通用功能下沉为平台基础设施。实现应用与平台基础设施的解耦。 服务网格的技术发展上数据平面与控制平面间的协议标准化是必然趋势。
