信息系统架构

信息系统设计的一个核心问题是能否使用重复的信息系统架构模式，即能否达到架构级别的软件重用。即能否在不同的软件系统中使用同一架构。 信息系统架构风格是描述某一特定应用领域中系统组织方式的惯用模式。 约束指出系统是如何将构件和连接件组合起来的。 根据特定项目的具体特点选择或设计特写的架构风格：

  • 数据流风格：批处理序列，管道、过滤器
  • 调用、返回风格：主程序、子程序，面向对象风格，层次结构
  • 独立构件风格：进程通信，事件系统
  • 虚拟机风格：解释器，基于规则的系统
  • 仓库风格：数据库系统，超文本系统，黑板系统 信息系统架构分类：
  1. 信息系统物理结构
    • 在空间上的拓扑关系
    • 集中式结构
      • 物理资源有空间上集中配置
      • 优点
        • 资源集中
        • 便于管理
        • 资源利用率较高
      • 缺点
        • 维护、管理比较困难
        • 不利于用户发挥在信息系统建设过程中的积极性与主动性
        • 过于集中会造成系统的脆弱
    • 分布式结构
      • 通过计算机网络把不同地点的计算机硬件、软件、数据等资源联系在一起，实现不同地点的资源共享。
      • 分布式结构已经成为信息系统的主流模式。
      • 优点
        • 按需配置资源
        • 安全性好。一个结点出现故障不会导致整个系统停止运作
      • 缺点
        • 系统管理的标准不统一。
      • 分类
        • 一般分布式
        • 客户机、服务器
  2. 信息系统的逻辑结构
    • 信息系统的逻辑结构是其功能综合体和概念性框架
    • 一个完整的信息系统支持组织的各种功能子系统
    • 将信息系统按职能划分成一个个职能子系统，然后逐个研制和开发。
    • 强调各子系统之间的协调一致性和整体性。
    • 横向综合
    • 纵向综合
    • 纵横综合

ADM 架构开发方法

The Open Group Architecture Framework TOGAF 是一种开放式企业架构框架标准。由国际标准权威组织 The Open Group 制定。 它是基于一个迭代(Iterative)的过程模型，支持最佳实践和一套可重用的现有架构资产。 功能：

  • 确保从关键利益相关方到团队成员的所有用户都使用相同的语言。
  • 避免被“锁定”到企业架构的专有解决方案。
  • 节省时间和金钱，更有效地利用资源。、
  • 实现可观的投资回报。 TOGRF 的 6 个组件：
  • 架构开发方法 Architecture Development Method ADM. 即一种开发企业架构的分步方法。
  • ADM 指南和技术 可用于应用 ADM 的指南和技术
  • 架构内容构架
  • 企业连续体和工具
  • 参考模型：技术参考模型、集成信息基础设施参考模型
  • 架构能力框架 其框架的核心思想：
  • 模块化架构
  • 内容框架
  • 扩展指南
  • 架构风格

预备阶段

  • A. 架构愿景 将启动一次架构开发过程的迭代，设置迭代工作的范围、约束、期望，创建架构愿景、验证业务上下文，创建架构工作说明书并取得大家的一致认可。
  • B. 业务架构 将开发一个支持架构愿景的业务架构。架构愿景中概括的基线和目标业务架构将在此被细化，从而使它们可以作为技术分析的有效输入。
  • C. 信息系统架 确定主要的信息类型和处理这些信息的应用系统。在本阶段有 2 个主要的步骤，数据架构设计和应用架构设计。二者可以依次开发，也可以并行开发。
  • D. 技术架构 完成对系统基础服务设施的设计，定义了架构解决方案的物理实现。
  • E. 机会及解决方案 确定目标架构交付物
  • F. 迁移规划 制订一个详细的实现和迁移计划，完成从基线架构向目标架构的转变。
  • G. 实施治理 实施项目的架构结束，提供项目构建的架构监督，产生一个架构契约。
  • H. 架构变更治理 确保以一种可控制的方式对架构的改变进行管理。
  • 需求管理 是一个动态的过程，完成对企业需求的识别、存储并把它们插入或取出相应的 ADM 阶段。它是 adm 流程的中心。

工厂模式在数据访问层应用

数据库的访问需要良好的封装性和可维护性。 工厂模式定义一个用于创建对象的接口，让子类决定实例化哪个类。

interface DataAccess {
  DatabaseType: () => DatabaseType
  DbConnection: () => IDbConnection
  Open: () => void
  Close: () => void
  BeginTransaction: () => IDbTransaction
  ExecuteNonQuery: (commandText: string) => number
  ExecuteDataset: (commandText: string) => dataSet
}
// 工厂函数
class DataAccessFactor {
  constructor() {
    this.defaultPersistenceProperty = {}
  }
  CreateDataAccess(pp) {
    switch (pp.databaseType) {
      case DatabaseType.MSSQLServer:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
      case DatabaseType.Oracle:
        dataAccess = new OracleDataAccess(pp.connectionString)
        break;
      case DatabaseType.OleDBSupported:
        dataAccess = new OleDbDataAccess(pp.connectionString)
        break;
      default:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
    }
  }
  static DataAcess() {
    return CreateDataAccess(defaultPersistenceProperty)
  }
}

事务处理设计

事务是现代数据库的核心概念之一。 ACID 原则：

  • 原子性 atomicity 表示事务执行过程中的任何失败都导致事务所做的任何修改失效。
  • 一致性 consistency 表示当事务执行失败时，所有被该事务影响的数据都恢复到事件执行前的状态。
  • 隔离怀 isolation 表示在事务执行过程中对数据的修改，在事务提交之前对其他事务不可见。
  • 持久性 durability 表示已提交的数据在事务执行失败时，数据的状态都应该正确。 常见的事务：
  • JDBC 事务
  • JTA 事务
  • 容器管理事务

云原生架构原则

云原生架构是一种架构，有若干架构原则作为应用架构的核心架构控制面，通过遵从这些架构原则可以让技术主管和架构师在做技术解决时不会出现大的偏差。

服务化原则
  • 当代码量超出小团队的合作范围时，就有必要进行服务化拆分。
  • 通过服务化架构把不同生命周期的模块分离出来，分别进行业务迭代。
  • 服务化架构以面向接口编程
  • 模块间通过公共功能模块的提取增加软件的复用程序。 分布式环境下的限流降级、熔断隔仓、灰度、反压、零信任安全等，本质是是基于服务流量的控制策略。所以云原生架构强调使用服务化的目的还在于从架构层面抽象化业务模块之间的关系，标准化服务流量的传输，从而帮助业务模块进行基于服务流量的策略控制和治理。
弹性原则

系统的部署规模可以随着业务量的变化而自动伸缩，无须根据事先的容量规划准备固定的硬件和软件资源。

可观测原则
韧性原则

代表了当软件所依赖的软硬件组件出现各种异常时，软件表现出来的抵御能力。 核心目标是提升软件的平均无故障时间（Mean Time Between Failure MTBF） 韧性包括：

  • 异步化能力
  • 重试
  • 限流
  • 降级
  • 熔断
  • 反压 当下游处理能力不足时，向上游施压，以减小数据发送速率。
  • 主从模式
  • 集群模式
  • AZ（同城多可用区）内的高可用
  • 单元化
  • 跨 Region 容灾
  • 异地多活容灾
所有过程自动化原则
  • 标准化企业内部的软件交付过程
  • 在标准化的基础上进行自动化
零信任原则

默认情况下不应该信任网络内部和外部的任何人、设备、系统，需要基于认证和授权重构访问控制的信任基础。

架构持续演进原则

在整个软件生命周期里面往往需要对架构进行一定范围内的重构。

主要架构模式

服务化架构模式

是云时代构建云原生应用的标准架构模式：

  • 以应用模块为颗粒度划分一个软件。
  • 以接口契约（如 idl）定义彼此业务关系
  • 以标准协议（http/grpc）确保彼此的互联互通
  • 结合 ddd/tdd/容器化部署提升每个接口的代码质量和迭代速度。 通过服务化架构，把代码模块关系和部署关系进行分离，每个接口可以部署不同数量的实例。
mesh 化架构模式

把中间框架从业务进程是分离，让中间件 sdk 与业务代码进一步解耦，从而使中间件升级对业务进程没有影响，甚至迁移到另外一个平台的中间件也对业务透明。

serverless 模式

当业务流量到来（业务事件发生）时，云会启动或调度一个已启动的业务进程进行处理，处理完成后云自动会关闭（调度业务进程），等待下一次触发，也就是把应用的整个运行都委托给云。 不适合情况：

  • 应用有状态
  • 长时间后台运行的密集型计算任务的应用
  • 应用涉及频繁的外部 i/o 适合情况
  • 事件驱动的数据计算任务
  • 计算时间短的请求、响应应用
  • 没有复杂互相调用的长周期任务
存储计算分离模式

分布式环境中 cap 困难主要是针对有状态应用。 c 一致性 a 可用性 p 分区容错性 在云环境中，推荐把各类暂态数据、结构化、非结构化持久数据把采用云服务来保存，从而实现存储计算分离。

分布式事务模式
  • 传统采用 XA 模式，虽然具备很强的一致性，但是性能差。
  • 基于消息的最终一致性 BASE 通常有很高的性能，但是通用性有限。
  • TCC 模式完全由由应用层来控制事务，事务隔离性可控，也可以做到比较高效；但是对业务侵入性非常强，设计开发维护等成本很高。
  • SAGA 模式与 TCC 模式的优缺点类似但没有 try 这个阶段，而是每个正向事务都对应一个补偿事务，也是开发维护成本高。
  • 开源项目 SEATA 的 AT 模式非常高性能且无代码开发工作量，且可以自动执行回滚操作，同时也存在一些使用场景限制。
可观测架构

包括:

  • Logging
    • 提供多个组织的详细信息跟踪 verbose/debug/warning/error/fatal
    • 由应用的开发者主动提供。
  • Tracing
    • 提供一个请求从前端到后端的完整链路跟踪
    • 对于分布式场景尤其有用
  • Metrics
    • 提供对系统量化的多维度度量
事件驱动架构 event driven architecture EDA

本质是一种应用、组件间的集成架构模式。 事件驱动不仅用于（微）服务解耦，还可用于：

  • 增强服务韧性
    • 服务间是异步集成的。下游服务器的运行状态不影响上游服务器。
  • command query responsibility segregation CQRS
    • 把对服务状态有影响的命令用事件来发起。
    • 对服务状态无影响的命令用同步调用的 api 接口。
    • 可以用于维护数据变更的一致性。
  • 数据变化通知
  • 构建开放式接口
  • 事件流处理 在 iot 时代大量传感器产生的数据，不会像人机交互一样需要等待处理结果的返回，天然适合用 eda 来构建数据处理应用。

SOA 的作用

SOA 凭借其松耦合的特性，使得企业可以按照模块化的方式来添加新服务或更新现有服务，以解决新的业务需要，提供选择从而可以通过不同的渠道提供服务，并可以把企业现有的或已有的应用作用为服务，从而保护了现有的 it 基础建设投资。 SOA 对实现企业资源共享，打破“信息孤岛”的步骤：

  1. 把应用和资源转换成服务
  2. 把这些服务变成标准的服务，形成资源的共享 SOA 不仅仅是一种技术，也是一种软件架构。企业的决策者只需要根据企业的策略来制定流程，把应用作为服务“拿来就用”，而无需考虑底层的集成。这样可以实现 it 和企业业务之间同步。

企业服务总线模式

像微核模式 对于点对点的集成方式存在复杂度高、可管理性差、复用度差、系统脆弱等问题。企业服务总线 Enterprise Service bus esb 在此背景下产生了。 功能：

  • 提供一种标准的软件底层架构，各种程序组件能够以服务单元的方式“插入”到该平台上运行。
  • 组件之间以标准的消息通信方式进行交互。
  • 提供位置透明性的消息路由和寻址服务
  • 提供服务注册和命名的管理功能
  • 支持多种消息传递范型（请求/响应，发布/订阅）
  • 支持多种可以广泛使用的传输协议
  • 支持多种数据格式及其相互转换
  • 提供日志和监控功能。 本质是中间件形式支持服务单元之间进行交互的软件平台。 交互过程：
  1. 由服务请求者发出一具满足 ESB 要求的请求。
  2. esb 根据消息中的服务名或者接口名进行目的组件查找，将消息转发给目的组件。
  3. 将处理结构逆向发给服务请求者。 作用：
  • 解耦组件之间的依赖关系，降低软件系统互联复杂性。
  • 连接在总线上的组件无需了解其他组件和应用系统的位置及交互协议。只需要向服务总线发请求。 收益：
  • esb 使得企业内部以及外部系统之间可以很容易地进行异步或同步交互
  • 采用面向服务的架构为系统提供了易扩展性和灵活性，在提高集成应用的开发效率的同时降低了成本。
  • esb 技术克服了传统应用集成技术的缺陷，能够对各种技术和应用系统提供支持。具有灵活性和可扩展性。

  • 在监控、管理、分发、扩容有巨大挑战。 取舍 考虑开发团队规模、业务需求变化、系统用户群体规模等诸多因素。使用微服务主要是为了降低应用程序开发、维护等方面的复杂性，如果系统程序无法再扩展、或数据增长速度过快，整个团队都具备微服务思维，采用微服务架构的收益会大于成本。

实时系统是指那些对“时间”有严格要求的计算机系统。 由于嵌入式系统中大部分领域是实时系统， 许多嵌入式操作系统都支持优先级抢占调度算法和时间片轮转调度算法。 在嵌入式强实时系统中，操作系统必须支持执行一组并发实时任务，使所有时间关键任务满足其指定的截止时限。 在实时系统的任务调度中，存在大量的实时调度方法：

  • 离线 off-line 和 在线 on-line
    • 按获得调度信息的时机
    • 离线：在运行过程中使用的调度信息在系统运行前确定。
      • 具有确定性。缺乏灵活性。
      • 适用于特征能够预先确定，且不容易发生变化的应用。
    • 在线：在系统运行过程中动态获得。
      • 灵活

    • 按任务在运行过程中能否被打断的处理情况。
    • 抢占：正在运行的任务可能被其他任务打断。
    • 非抢占：正在运行的任务不能被其他任务打断。
  • 静态 static 和 动态 dynamic
    • 按任务优先级确定。
    • 静态：在设计时确定下所有任务的优先级，
      • 适用于能完全把握系统中所有任务及其时间约束。
      • 简单，缺乏灵活性，
      • 不利于系统扩展

    • 按任务的截止时间确定任务的优先级。截止时间越早越优先。
    • 总是执行任务队列中第一个任务
  • 最低松弛度优先 Least Laxity First LLF
    • 按任务紧急程序确定优先级。
  • 单调速率调度算法 Rate Monotonic Scheduling RMS
    • 是一种静态优先级调度算法，是经典的周期性任务调度算法。
    • 任务的周期越短，优先级越高。
    • 单调速率调度可认为是最优的。因为若一组进程不能由此算法调度，则不能由任务其他分配静态优先级的算法调度。 存储管理 其管理的对象是主存，也称内存。 主要功能：

    • 可变分区
      • 按作业的大小划分分区
      • 可以克服固定分区方式中的主存空间的浪费
      • 调度算法：
        • 首次适应算法 按顺序查找未分配的表，找到第一个满足长度要求的空闲区。
        • 最佳适应算法 在空闲区中找满足作业要求的最小分区
        • 最坏适应算法 在空闲区中找最大分区

      • 在作业的动态运行时装入内存的所有地址都是一个相对地址（即逻辑地址），将相对地址转换为物理地址的工作，被推迟到程序指令要真正执行时进行。
  • 分页储管理
    • 将一个进程的逻辑地址空间分成若干个大小相等的片。称为页面或页。
  • 分段存储管理
    • 作业的地址空间被分成若干段，每个段定义一组逻辑信息。

状态机模型

状态机模型描述了一种无论处于何种状态都是安全的系统。 状态机模型中一个状态是处于系统的特定时刻的一个快照。 只允许主体以和安全策略相一致的安全方式访问资源。 具体步骤：

  1. 状态变量的默认值必须安全
  2. 用户试图使用变量的默认值
  3. 系统检查主体的身份验证
  4. 系统确保变更不会使系统置于不安全状态
  5. 系统允许变量值变更，发生状态改变
  6. 再重复执行 1-5 步，会导致另一次状态变化。

Chinese Wall 模型

应用在多边安全系统中的完全模型。 模型基本原理 基础是客户访问的信息不会与当前他们可支配的信息产生冲突。 模型的安全规则

  • 与主体曾经访问过的信息属于同一公司数据集合的信息，即墙内信息可以访问
  • 属于一个完全不同的利益冲突组的可以访问
  • 主体能够对一个客体进行写的前提是主体未对任何属于其他公司数据集进行过访问。 定理一：一个主体一旦访问过一个客体，则该主体只能访问位于同一公司数据集的客体或在不同利益组的客体。 定理二：在一个利益冲突组中，一个主体最多只能访问一个公司数据集。

数据库的完整性设计

指数据库中数据的正确性和相容性。 数据库的完整性设计原则

  • 根据数据库完整性约束的类型确定其实现的系统层次和方式，并提前考虑对系统性能的影响。
  • 实体完整性约束、引用完整性结束是关系数据库最重要的完整性约束，不影响系统关键性能的前提下需要尽量应用。
  • 要慎用目前主流 DBMS 都支持的触发器功能，最好使用 Before 型语句级触发器。
  • 需求分析阶段就必须制定完整性约束的命名规范。
  • 要根据业务规则对数据库完整性进行细致的测试，以尽早排队隐含的完整性约束童年冲突和性能的影响。
  • 要有专职的数据库设计小组，自始至终负责数据库的分析、设计、测试、实施、早期维护。
  • 应采用合适的 CASE 工具来降低数据库设计各阶段的工作量。 数据库的完整性的作用
  • 能够防止合法用户使用数据库时向数据库中添加不合语义的数据。
  • 利用基于 DBMS 的完整性控制机制来实现业务规则，易于定义，容易理解，而且可以降低应用程序的复杂性，提高应用程序的运行效率。
  • 合理的数据库完整性设计，能够同时兼顾数据库的完整笥和系统的效能。
  • 在应用软件的功能测试中，完善的数据完整性有助于尽早发现应用软件的错误。

    • 关系级静态约束
    • 列级动态约束
    • 元组级动态约束
    • 关系级动态约束 数据库完整性设计示例

  • 旧的脆弱性得到修补或纠正的同时可能引入新的脆弱性，因此脆弱性问题会长期存在。

Lambda 架构对大数据处理系统的理解

设计目的在于提供一个能满足在数据系统关键特性的架构。

Lambda 架构应用场景

  • 机器学习中的 Lambda 架构

  • 物联网中的 Lambda 架构

  • 流处理和 Lambda 架构挑战
    • 速度层仅关心自完成最后一组批处理视图以来导入的数据。该层不保存数据。
    • 批处理层更关注精确计算，而速度层则关注近似计算。

Lambda 架构介绍

  • 批处理层 Batch Layer
    • 预先计算查询函数，并构建查询所对应的 view。
    • 该层用于处理离线数据。
    • 该层中数据的三个属性：
      • 数据是原始的。
      • 数据是不可变的
      • 数据是真实的
    • 从业务需求出发，所有需要的查的是有限的。
  • 速度层 Speed Layer
    • 该层处理最近的增量数据流，在收到数据后不断更新 Real-time View
  • 服务层 Serving Layer
    • 合适批处理层和速度层的结果。
    • 利用了范畴学的 Monoid 概念，它满足结合律。
      map reduce 进行大量数据处理
      产生批处理结果视图
      结果认为是精准且全量的
      数据处理时延很高
                |
                |
               批处理层 ----|
  数据源 ----->             |--> 服务层 ---> 查询视图
               速度层  -----|     |
                |                |
                |             汇总流处理视图和批处理视图
                |             产生查询视图
                |
                |
      只处理最近产生的实时数据
      产生流处理结果视图
      流处理层的数据可能不准确，也不全量
      数据处理时延很低

优点：

  • 容错性 在批处理层重新计算时修正引入的错误
  • 复杂性隔离 把复杂性隔离到速度层，提高了整个系统的鲁棒性和可靠性
  • 横向扩容 Scalable 当数据量大时，通过增加更多的机器资源来维持性能，（不是增强机器的性能）。三层都可以分布式扩展。
  • 查询灵活度高，批处理层允许对任任何数据进行临时查询。 缺点：
  • 全场景覆盖带来的编码开销
  • 针对具体场景重新离线训练一遍益处不大
  • 重新部署和迁移成本高

做好准备工作

论文试题是考查考生在系统架构设计方面的经验和综合能力，以及表达能力，目的：

  • 检查考生是否具有参加系统架构设计工作的实践经验

  • 经验丰富的应考人员，主要是将自己的经验进行整理，从技术、管理、经济方法等多个角度对自己做过的项目进行归纳、剖析、抽象和升华，在总结的基础上，结合专业知识和关键技术进行分类和梳理。

写作技巧
以自我为中心。

论文考核的是以考生作为系统架构设计师的角度对系统的认知能力。 考生必须清楚地说明针对具体项目自己所做的事情的由来，遇到的问题，解决方法和实施效果。 体现实力是考生做了些什么。

  • 体现实际经验。
  • 条理性地说明实际经验
  • 写明项目一切体制和规模
  • 明确“我”的工作任务和所起的作用
  • 以“我”在项目中的贡献为重点说明。
  • 以“我”怎样做出贡献为中心说明。
站在架构师的角度

论文考核的是考生以架构师的角度对系统的认知能力，要求全面，详尽地考虑问题。 如写有关层次式架构设计的论文，考生就要从全局的角度把握：

  • 层次式架构设计的优点及缺点
  • 设计层次式架构的方法和过程 特别是各层次之间的接口设计问题，而不是专注于某个具体的实现细节。
忠实于论点

首先是建立在正确理解题意的基础上，根据正确的题意提取论点加以阐述。阐述时要绝对服从论点。就试题的问题进行展开。

条理清晰，开门见山

论文的组织一定要条理清晰。题目选定后，要迅速整理自己所掌握的素材，列出提纲，即打算谈几个方面，每个方面是怎么做的，收效如何。简明扼要地写在草稿纸上。 侧重点在汇报考生在项目中所做的与论题相关的工作。提纲不要求全面，关键要列出自己所做过的工作。 让专家短时间内了解考生的论文内容并认可考生的能力，必须把握好主次关系。 一般来说，第一部分的项目概念对评卷专家掌握整个论文非常重要，考生要学会用精练的语句说明项目的背景、意义、规模、开发过程以及自己的角色等，让证券专家对自己所做的项目产生兴趣。

标新立异，要有主见

若评卷专家看到考生的论文有一种深爱启发、耳目一新的感觉，结果会好。 一定要动脑筋写一些个人的见识和体会。

图文并茂，能收奇效

图形比文字更能吸引人的注意力，更加简洁、明了。通过图形方式表达，更能让评卷专家直观地了解考生所设计的架构，从而得到专家的认可。

首尾一致

在正文的写作中，要做到开头与结尾互相呼应。 言词与论文试题的提法一致。
