论网络安全体系架构设计

摘要

2023 年 3 月，我参与了某省级医保移动支付结算平台的建设，担任系统架构设计师，负责整体安全架构设计与技术选型。该平台覆盖全省定点医疗机构与药店，需在互联网暴露面下处理参保人身份核验、处方流转与基金结算等敏感业务，安全要求极为严格。本文以该项目为例，论述网络安全体系架构设计的实践过程。平台面临的主要威胁包括身份冒用、数据泄露与越权访问。我们依据等级保护三级要求，从鉴别服务、访问控制、数据机密性与完整性、安全审计与边界防护四个维度构建纵深防御体系：采用多因子认证与国密证书实现强身份鉴别；以 RBAC 与 ABAC 混合模型实施最小权限管控；通过传输加密与字段级脱敏保障数据全生命周期安全；部署分区隔离与全流量审计实现可追溯可定责。平台上线后通过第三方安全测评，高危漏洞清零，运行至今未发生安全事件，有效保障了医保基金与参保人信息安全。

正文

一、项目背景与主要工作

2023 年 3 月，我所在公司中标某省医疗保障局“医保移动支付结算平台”建设项目。该项目旨在打通定点医疗机构、定点药店与医保经办机构之间的线上结算通道，支持参保人通过移动端完成挂号、诊间支付、处方流转与药品配送全流程。平台采用微服务架构，基于 Spring Cloud 生态构建，部署于省政务云环境，需与省级医保核心系统、电子凭证系统、银联支付网关及数十家医院 HIS 系统对接。系统日均交易量设计峰值为 50 万笔，覆盖全省 2.3 万家定点机构，属于典型的高并发、强监管、高安全要求的民生类系统。

我在项目中担任系统架构设计师，主要职责包括：整体技术架构设计、安全架构专项设计、中间件与安全组件选型、以及开发过程中的安全评审与合规把关。项目组共 28 人，其中安全专职 2 人。项目于 2023 年 12 月通过初验，2024 年 3 月正式上线运行。

二、网络安全架构设计的涵盖方面与安全实现

网络安全架构设计不是单一产品的堆砌，而是一个覆盖“识别—防护—检测—响应”全链路的体系。在本项目中，我从以下四个层面展开设计。

（一）身份鉴别与访问控制

身份鉴别解决“你是谁”的问题，访问控制解决“你能做什么”的问题。医保场景中，用户角色涵盖参保人、医师、药师、药店店员、经办管理员等，不同角色对数据的敏感度差异极大。鉴别层面，参保人端采用“人脸识别+短信验证码”双因子认证，医师与药师端强制使用国密数字证书登录，管理员端额外绑定设备指纹。访问控制层面，采用 RBAC 与 ABAC 相结合的混合模型：RBAC 定义角色基线权限，ABAC 根据访问上下文（时间、地点、数据敏感等级、操作类型）进行动态裁决。例如，药店店员仅能在营业时间访问本店处方数据，且禁止批量导出操作。该设计遵循最小权限原则，有效降低了越权访问与账号盗用风险。

（二）数据机密性与完整性保护

医保数据涉及个人健康信息与基金交易记录，机密性与完整性缺一不可。传输层面，全链路启用 TLS 1.3，内部微服务间采用 mTLS 双向认证。存储层面，对身份证号、银行卡号、诊断信息等敏感字段实施字段级加密，密钥由硬件密码机托管，应用系统不接触明文密钥。完整性方面，关键交易数据（如结算金额、处方明细）在写入数据库前生成 SM3 摘要并落库，后续任何读取操作均需校验摘要一致性，防止数据在存储或传输环节被篡改。此外，对开发与测试环境实施数据脱敏，避免真实数据在非生产环境泄露。

（三）安全区域边界与网络隔离

依据等级保护三级要求，我将系统划分为互联网接入区、DMZ 区、应用服务区与核心数据区四个安全域。互联网区仅暴露移动端 API 网关与静态资源，经 WAF 清洗后进入 DMZ；DMZ 部署反向代理与 API 鉴权网关，完成协议转换与令牌校验；应用服务区运行微服务集群，禁止直接访问数据库；核心数据区部署数据库与密码机，仅接受来自应用服务区的白名单连接。各区域间通过防火墙策略实施最小化放通，东西向流量由微隔离组件管控。这一分区架构将攻击面收敛到可控边界，即便某一层被突破，攻击者也无法横向移动至核心数据区。

（四）安全审计与持续监测

安全审计是事后追溯与责任认定的基础。平台在网关层、应用层与数据库层分别部署审计探针，记录全量访问日志与敏感操作日志。日志统一汇入 ELK 集群，留存期限不少于六个月。同时配置实时告警规则：同一账号短时间多地登录、非工作时间访问敏感数据、批量查询患者信息等行为触发即时告警并推送至安全运营值班群。审计日志本身采用只追加写入与哈希链校验，防止被篡改或删除。这一设计使安全事件的平均发现时间从小时级压缩至分钟级。

三、采用的网络安全架构设计方法与实施效果

在上述框架下，我重点采用了三种具体方法，并在项目中取得了可验证的效果。

方法一：基于威胁建模的架构风险前置识别

在详细设计阶段，我组织安全专员与核心开发人员，采用 STRIDE 方法对数据流图进行逐层威胁建模。以“处方流转”流程为例，识别出欺骗（医师身份伪造）、篡改（处方金额被修改）、抵赖（医师否认开方行为）三类主要威胁。针对欺骗威胁，在处方开具接口增加数字签名与时间戳，医师使用个人证书对处方内容签名，服务端验签通过后方可入库；针对篡改威胁，处方明细与金额绑定 SM3 摘要；针对抵赖威胁，签名日志与处方原文一并归档。威胁建模使安全控制点在设计阶段即被明确，避免了上线后“打补丁”式的被动修复。实施后，处方流转模块在第三方渗透测试中未发现高危缺陷。

方法二：基于零信任理念的 API 安全网关设计

平台对外暴露的 API 超过 120 个，传统基于边界的安全模型难以应对凭证泄露后的横向调用。我设计了统一的 API 安全网关，所有调用方（包括内部微服务）必须携带由网关签发的短期 JWT 令牌，令牌中嵌入调用方身份、角色与可访问的 API 白名单。网关对每个请求执行“认证—鉴权—限流—审计”四步流水线。对于高敏感接口（如基金拨付查询），额外要求请求方提供由密码机生成的动态签名。该网关上线后，成功拦截了多次来自合作方系统的异常批量查询请求，日均阻断未授权调用约 300 次，有效防止了数据爬取与接口滥用。

方法三：安全左移与持续合规检查

将安全活动嵌入 DevSecOps 流水线。在代码提交阶段，SonarQube 静态扫描检测 SQL 注入、硬编码密钥等缺陷，高危问题阻断合并；在构建阶段，对容器镜像进行 CVE 漏洞扫描，基础镜像仅允许来自内部受信仓库；在部署阶段，通过配置核查脚本自动校验安全组规则、数据库加密开关、日志采集状态是否符合基线要求，不合规的部署包禁止发布至生产环境。安全左移实施后，生产环境中的配置类安全问题同比下降约 70%，安全团队从“上线前救火”转向“过程中管控”，整体交付效率反而提升。

实施效果

平台于 2024 年 3 月上线，同年 5 月通过第三方测评机构的安全等级保护三级测评，渗透测试报告中高危漏洞数为零。上线至今运行超过 12 个月，累计交易笔数突破 1800 万笔，未发生数据泄露、越权访问或基金盗刷等安全事件。安全审计系统累计触发并处置有效告警 47 次，均为合作方接口异常调用与用户异地登录，均在 15 分钟内完成闭环。项目获得省医保局书面表扬，安全架构设计方案被作为模板推广至该局其他信息化项目。

结语

回顾该项目，网络安全体系架构设计的核心不在于部署了多少安全设备，而在于是否将安全能力嵌入业务流程与研发生命周期。鉴别与访问控制管住“人”，机密性与完整性管住“数”，分区与审计管住“路”与“责”，而威胁建模与安全左移则让架构在设计和开发阶段就具备抵御风险的结构性优势。后续我将在零信任持续验证与数据分类分级自动化方向继续深化实践，为民生类信息系统的安全运行提供更坚实的架构支撑。
