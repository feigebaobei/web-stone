# 软件工程基础知识

## 软件工程

软件危机的具体表现：

- 软件开发进度难以预测
- 软件开发成本难以控制
- 软件功能难以满足用户期望
- 软件质量无法保证
- 软件难以维护
- 软件缺少适当的文档资料

## 软件工程定义

软件工程活动包括：

- Plan 软件规格说明，规定软件的功能及其运行时的限制。
- Do 软件开发，开发出满足规格说明的软件。
- Check 软件确认，确认开发的软件能够满足用户的需求。
- Action 软件演进，软件在运行过程中不断改进以满足客户的新需求

### 软件过程模型

瀑布模型 Waterfall Model

```
  需求分析
    系统设计
      程序设计
        编码实现
          单元测试
            集成测试
              系统测试
                运行维护
```

特点：因果关系紧密相连，前一个阶段工作的输出结果，是后一个阶段工作的输入，每一个阶段都是建筑在前一个软件正确实施的结果之上。每一个阶段完成后都伴随着一个里程碑，对该阶段的工作进行审查和确认。
缺点：

- 软件需求的完整性、正确性等很难确定。
- 瀑布模型是一个严格串行的过程模型，使得用户和软件项目负责人要相当长的时间才能得到一个可以看得见的软件系统。
- 瀑布模型的基本原则是在每个阶段一次性地完成解决该阶段的工作，不会出现遗漏、错误等情况，而实际上这是不现实或不可能的。

原型化模型 Prototype Model 也称为快速原型。

```
  需求分析 -------|
    系统设计 -----|-- 原型开发
      程序设计 ---|
        编码实现
          单元测试
            集成测试
              系统测试
                运行维护
```

分为 2 个阶段：

- 原型开发阶段。软件开发人员根据用户提出的软件系统的定义，快速开发一个原型。该原型应该包括目标系统的关键问题和反映目标系统的大致面貌，展示目标系统的全部或部分功能、性能等。
- 目标软件开发阶段。在征求用户对原型的意见后对原型进行修改完善，确认软件系统的需求并达到一致的理解，进一步开发实际系统。

抛弃型原型是将原型作为需求确认的手段，在需求确认结束后，原型就被抛弃不用，重新采用一个完整的瀑布模型进行开发。
演化型原型是在需求确认结束后，不断补充和完善原型，直至形成一个完整的产品。

螺旋模型 Spiral Model 是在快速原型的基础上扩展而来的。此模型把软件开发分成多个阶段，每个阶段由 4 部分组成：

- 目标设定。为该项目进行需求分析，定义和确定这一阶段的专门目标，制定对过程和产品的约束，并且制订详细的管理计划。
- 风险分析。对可选方案进行风险识别和详细分析，制定解决方案，采取有效措施避免这些风险。
- 开发和有效性验证。风险评估后，可以为系统选择开发模型，并且进行原型开发。
- 评审。对项目进行评审，以确定是否需要进入螺旋线的下一次回路。

### 敏捷模型

特点：

- 适应性而非预设性
- 面向人而非面向过程。
  - 体现在这 3 个方面：
    - 开发人员必须有权做技术方面的所有决定。
    - 特别强调开发中相关人员之间的信息交流。
    - 特别提倡直接的面对面交流。

敏捷方法的核心思想：（3 点）

- 是适应型的，非可预测型的。
- 以人为本的，非以过程为本的。
- 迭代增量式的开发过程。

主要的敏捷方法：

- 极限编程 Extreme Programming XP
- 水晶系统方法
- Scrum
- 特性驱动开发方法 Feature Driven Development FDD

### 统一过程模型 Rational Unified Process RUP

生命周期：

- 业务建模
- 需求
- 分析与设计
- 实现
- 测试
- 部署
- 配置与变更管理
- 项目管理
- 环境

核心概念：

- 角色
- 活动
- 制品
- 工作流

rup 的特点：

- 用例驱动的
- 以体系结构为中心
- 迭代和增量

4+1 视图：

- 逻辑视图
- 实现视图
- 进程视图
- 部署视图
- 用例视图

### 软件能力成熟度模型 Capability Maturity Model for Software CMM

- level1 初始级。过程是随意且混乱的。
- level2 已管理级。组织要确保策划、文档化、执行、监督和控制项目级的过程，并且需要为过程建立明确的目标，能实现成本、进度和质量目标等。
- level3 已定义级。企业根据自身的实际情况定义适合的项目标准流程，并将这套管理体系与流程制度化。
- level4 量化管理级。在已定义级别上增加对过程性能的可预测。
- level5 优化级。通过增量式的与创新式的过程与技术改进，不断地改进过程性能。

## 需求工程

需求包括 3 个层次:

- 业务需求 business requirement 反映了组织机构或客户对系统、产品高层次的目标要求。
- 用户需求 user requirement 描述了用户使用产品必须要完成的任务。
- 功能需求（也包括非功能需求） functional requirement 定义了开发人员必须实现的软件功能，使得用户能完成他们的任务。

需求工程的活动可以分为 5 个阶段：

1. 需求获取。通过对用户的交流，对现有系统的观察及对任务进行分析，从而开发、捕获和修订用户的需求。
2. 需求分析。为系统建立概念模型，作为对需求的抽象描述，并尽可能多的捕获现实世界的语义。
3. 形成需求规格（或称为需求文档化）。按照相关标准，生成需求模型的文档描述，用户原始需求书作为用户和开发者之间的一个协约。
4. 需求确认与验证。以需求规格说明为输入，通过用户确认、复审会议、符号执行、模拟仿真或快速原型等途径与方法，确认和验证需求规格的完整性、正确性、一致性、可测试性和可行性，包含有效性、一致性检查和确认可验证性。
5. 需求管理。包括需求文档的追踪管理、变更控制、版本控制等管理性活动。

需求管理是一个对系统需求变更、了解和控制的过程。

### 需求获取

需求陈述应该阐明“做什么”，而不是“怎么做”。
需求获取的基本步骤：

1. 开发高层次的业务模型
2. 定义项目范围和高层需求
3. 识别用户角色和用户代表
4. 获取具体的需求
5. 确定目标系统的业务工作流
6. 需求整理与总结

需求获取方法：

- 用户面谈
- 需求专题讨论会
- 问卷调查
- 现场观察
- 原型化方法
- 头脑风暴法
