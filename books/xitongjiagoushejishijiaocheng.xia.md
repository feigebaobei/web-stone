### 信息系统架构基本概念及发展

对于大规模的复杂系统来说，总体的系统结构设计比计算算法和数据结构更重要。
信息系统的架构本质上存在 2 个层次：

- 概念层次
- 物理层次
  信息系统架构是关于软件系统的结构、行为和属性的高级抽象。
  企业架构框架是 TOGAF The Open Group Archietecture Framework, open group 架构框架
  几乎所有领域都能够和信息技术相结合 构成企业信息化项目。
  包括：
- 信息系统架构描述语言
- 信息系统架构的描述与表示
- 信息系统架构的分析与验证
- 基于架构的软件维护与演化
- 信息系统架构的可靠性
  关于其定义中的说明：
- 架构是系统的抽象
- 架构由多个结构组成
- 任何软件都存在架构
- 元素及其行为的集合构成架构的内容
- 架构具有“基础”性。
  - 通常涉及解决各类关键重复问题的能用方案
  - 系统设计中影响深远的各项重要决策
- 架构隐含有“决策”
  - 架构设计师根据功能与非功能需求进行设计与决策的结果
    影响架构的因素：
- 软件系统的干系人对其有不同的要求
- 开发组织有不同的人员知识结构
- 架构设计师的素质与经验
- 当前的技术环境
  这些因素也会影响架构。

### 信息系统架构

信息系统设计的一个核心问题是能否使用重复的信息系统架构模式，即能否达到架构级别的软件重用。即能否在不同的软件系统中使用同一架构。
信息系统架构风格是描述某一特定应用领域中系统组织方式的惯用模式。
约束指出系统是如何将构件和连接件组合起来的。
根据特定项目的具体特点选择或设计特写的架构风格：

- 数据流风格：批处理序列，管道、过滤器
- 调用、返回风格：主程序、子程序，面向对象风格，层次结构
- 独立构件风格：进程通信，事件系统
- 虚拟机风格：解释器，基于规则的系统
- 仓库风格：数据库系统，超文本系统，黑板系统
  信息系统架构分类：

1. 信息系统物理结构
   - 在空间上的拓扑关系
   - 集中式结构
     - 物理资源有空间上集中配置
     - 优点
       - 资源集中
       - 便于管理
       - 资源利用率较高
     - 缺点
       - 维护、管理比较困难
       - 不利于用户发挥在信息系统建设过程中的积极性与主动性
       - 过于集中会造成系统的脆弱
   - 分布式结构
     - 通过计算机网络把不同地点的计算机硬件、软件、数据等资源联系在一起，实现不同地点的资源共享。
     - 分布式结构已经成为信息系统的主流模式。
     - 优点
       - 按需配置资源
       - 安全性好。一个结点出现故障不会导致整个系统停止运作
     - 缺点
       - 系统管理的标准不统一。
     - 分类
       - 一般分布式
       - 客户机、服务器
2. 信息系统的逻辑结构
   - 信息系统的逻辑结构是其功能综合体和概念性框架
   - 一个完整的信息系统支持组织的各种功能子系统
   - 将信息系统按职能划分成一个个职能子系统，然后逐个研制和开发。
   - 强调各子系统之间的协调一致性和整体性。
   - 横向综合
   - 纵向综合
   - 纵横综合

### 信息系统架构设计方法

#### ADM 架构开发方法

The Open Group Architecture Framework TOGAF 是一种开放式企业架构框架标准。由国际标准权威组织 The Open Group 制定。
它是基于一个迭代(Iterative)的过程模型，支持最佳实践和一套可重用的现有架构资产。
功能：

- 确保从关键利益相关方到团队成员的所有用户都使用相同的语言。
- 避免被“锁定”到企业架构的专有解决方案。
- 节省时间和金钱，更有效地利用资源。、
- 实现可观的投资回报。
  TOGRF 的 6 个组件：
- 架构开发方法 Architecture Development Method ADM. 即一种开发企业架构的分步方法。
- ADM 指南和技术 可用于应用 ADM 的指南和技术
- 架构内容构架
- 企业连续体和工具
- 参考模型：技术参考模型、集成信息基础设施参考模型
- 架构能力框架
  其框架的核心思想：
- 模块化架构
- 内容框架
- 扩展指南
- 架构风格

##### ADM 架构开发方法

定义开发企业架构所需要执行各个步骤以及它们之间的关系。

###### ADM 的架构开发阶段

由一组按照架构领域的架构开发顺序而排列成一个环的多阶段所构成。
十个阶段是反复迭代的过程。
每个阶段都需要根据原始业务需求对设计结构进行确认。
3 个级别的迭代概念：

- 基于 ADM 整体的迭代
- 多个开发阶段间的迭代
- 在一个阶段内部的迭代。

```
                        预备阶段
                           ^
                           |
                           V
    H. 架构变更治理 <----> A. 架构愿景 <----> B. 业务架构
          ^ \              ^              / ^
          |   \            |            /   |
          |     \          |          /     |
          |       \        |        /       |
          |         \      |      /         |
          |           \    |    /           |
          V             \  V  /             V
    G. 实施治理 <----> 需求管理 <----> C. 信息系统架构
          ^             /  ^  \             ^
          |           /    |    \           |
          |         /      |      \         |
          |       /        |        \       |
          |     /          |          \     |
          |   /            |            \   |
          V /              V              \ V
    F. 迁移规划 <----> E. 机会及解决方案 <----> D. 技术架构
```

预备阶段

- A. 架构愿景 将启动一次架构开发过程的迭代，设置迭代工作的范围、约束、期望，创建架构愿景、验证业务上下文，创建架构工作说明书并取得大家的一致认可。
- B. 业务架构 将开发一个支持架构愿景的业务架构。架构愿景中概括的基线和目标业务架构将在此被细化，从而使它们可以作为技术分析的有效输入。
- C. 信息系统架 确定主要的信息类型和处理这些信息的应用系统。在本阶段有 2 个主要的步骤，数据架构设计和应用架构设计。二者可以依次开发，也可以并行开发。
- D. 技术架构 完成对系统基础服务设施的设计，定义了架构解决方案的物理实现。
- E. 机会及解决方案 确定目标架构交付物
- F. 迁移规划 制订一个详细的实现和迁移计划，完成从基线架构向目标架构的转变。
- G. 实施治理 实施项目的架构结束，提供项目构建的架构监督，产生一个架构契约。
- H. 架构变更治理 确保以一种可控制的方式对架构的改变进行管理。
- 需求管理 是一个动态的过程，完成对企业需求的识别、存储并把它们插入或取出相应的 ADM 阶段。它是 adm 流程的中心。

## 第 13 章 层次式架构设计理论与实践

### 层次式体系结构概述

软件体系结构不仅指定了系统的组织结构和拓扑结构，并且显示了系统需求和构成系统的元素之间的对应关系。
软件体系结构的影响：

- 利益相关人员之间交流
- 系统设计的前期决策
- 可传递的系统级抽象
  层次式体系结构设计是将系统组成一个层次结构，每一层为上层服务，并作为下层客户。
  每一层最多蛤影响 2 层。同时只为邻层提供相同的接口，允许每层不同的方法实现。同样为软件重用提供了强大的支持。
  每层都有一个功能、角色、职能。
  分层构架的特点是关注分离 seperation of concerns

```
        request
          |
          |
          V
  表现层       组件   组件   组件   组件   封闭
          |
          |
          V
  中间层       组件   组件   组件   组件   封闭
          |
          |
          V
  访问层       组件   组件   组件   组件   封闭
          |
          |
          V
  数据层       组件   组件   组件   组件   封闭
```

设计时注意：

- 要注意污水池反模式 architecture sinkhole anti-parttern
  - 请求流简单的穿过几个层，每层基本没有任何业务逻辑。
- 考虑分层构架可能会让应用变庞大

#### 表现层设计模式

##### mvc 模式

- 控制器 controller
  - 解释来自视图的输入，将其解释成为系统能够理解为对象，同时它也识别用户动作，并将其解释为对模型特定方法的调用。
  - 处理来自模型的事件和模型逻辑执行的结果，调用适当的视图为用户提供反馈。
- 模型 model
- 视图 view

```
        选择视图                           业务处理
  |------------------------ 控制器 -----------------------|
  |                     接受用户请求                       |
  |    |--------------> 调用模型响应用户请求                |
  |    |                选择视图显示响应结果                |
  |    | 用户请求                                         |
  |    |                                                 |
  V    |                                                 V
视图                                                     模型
显示模型状态                  状态查询               代表应用程序状态
接受数据更新请求        --------------------------> 响应状态查询
把用户输入数据传给控制器 <-------------------------- 处理业务流程
                           通知数据更新            通知视图业务状态更新
```

优点：

- 允许多种用户界面的扩展
- 易于维护
- 功能强大的用户界面
  常用于 web 应用框架。

##### mvp

model-view-presenter
所有的交互都发生在 presenter 内部。而在 mvc 中 view 是直接从 model 中取数据的。
presenter 负责逻辑的处理
model 提供数据
view 渲染视图

```
                         2. 行为通知                3. 改变model
user 1. 用户操作    view -------------> presenter  ------------> model
    ------------>       <------------             <------------
    <------------        5. model改变引起的通知       4. 获取改变后的数据
     7. 渲染输出   6. 渲染
```

优点：

- 模型与视图完全分离，可以修改视图而不影响模型
- 可以更高效地使用模型，因为所有的交互都发生在 presenter 内部。
- 可以不改变 presenter 的逻辑，将 presenter 用于多个视图。
- 可以脱离接口来测试 presenter 中的逻辑。（单元测试）
  常用于 android 开发。

##### mvvm

viewmodel 负责 view/model 之间的交互，它是核心。通过 dataBinding 实现 view、model 之间的双向绑定，其内容包括数据状态处理、数据绑定及数据转换。
viewmodel 是视图模型，是一个专门用于数据转换的控制器，它可以把对象信息转换为视图信息，将命令从视图携带到对象。
viewmodel 是一个观察者，当数据发生变化，viewmodel 能够监听到数据的变化，然后通知对应的视图做更新。
当用户操作视图，viewmodel 也能监听到视图的变化，出通知数据做改动，从面形成数据的双向绑定。
适用于数据驱动的场景，尤其是数据操作特别频繁的场景。

```
         dataBinding
  view ---------------> viewmodel ---------------> model
       <---------------           <---------------
         dom事件监听
```

```ts
class DataAccessFactor {
  constructor() {
    this.defaultPersistenceProperty = {}
  }
  CreateDataAccess(pp) {
    switch (pp.databaseType) {
      case DatabaseType.MSSQLServer:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
      case DatabaseType.Oracle:
        dataAccess = new OracleDataAccess(pp.connectionString)
        break;
      case DatabaseType.OleDBSupported:
        dataAccess = new OleDbDataAccess(pp.connectionString)
        break;
      default:
        dataAccess = new MSSQLDataAccess(pp.connectionString)
        break;
    }
  }
  static DataAcess() {
    return CreateDataAccess(defaultPersistenceProperty)
  }
}
```

#### 事务处理设计

事务是现代数据库的核心概念之一。
ACID 原则：

- 原子性 atomicity 表示事务执行过程中的任何失败都导致事务所做的任何修改失效。
- 一致性 consistency 表示当事务执行失败时，所有被该事务影响的数据都恢复到事件执行前的状态。
- 隔离怀 isolation 表示在事务执行过程中对数据的修改，在事务提交之前对其他事务不可见。
- 持久性 durability 表示已提交的数据在事务执行失败时，数据的状态都应该正确。
  常见的事务：
- JDBC 事务
- JTA 事务
- 容器管理事务

运行过程：

1. 建立静态连接池。（池中的连接是在系统初始化时分配好的，并且不能随意关闭。）
2. 当请求时，若存在空闲连接，则使用空间连接；否则共享一个合适的连接。

#### 云原生架构原则

云原生架构是一种架构，有若干架构原则作为应用架构的核心架构控制面，通过遵从这些架构原则可以让技术主管和架构师在做技术解决时不会出现大的偏差。

##### 服务化原则

- 当代码量超出小团队的合作范围时，就有必要进行服务化拆分。
- 通过服务化架构把不同生命周期的模块分离出来，分别进行业务迭代。
- 服务化架构以面向接口编程
- 模块间通过公共功能模块的提取增加软件的复用程序。
  分布式环境下的限流降级、熔断隔仓、灰度、反压、零信任安全等，本质是是基于服务流量的控制策略。所以云原生架构强调使用服务化的目的还在于从架构层面抽象化业务模块之间的关系，标准化服务流量的传输，从而帮助业务模块进行基于服务流量的策略控制和治理。

##### 弹性原则

系统的部署规模可以随着业务量的变化而自动伸缩，无须根据事先的容量规划准备固定的硬件和软件资源。

#### 主要架构模式

##### 服务化架构模式

是云时代构建云原生应用的标准架构模式：

- 以应用模块为颗粒度划分一个软件。
- 以接口契约（如 idl）定义彼此业务关系
- 以标准协议（http/grpc）确保彼此的互联互通
- 结合 ddd/tdd/容器化部署提升每个接口的代码质量和迭代速度。
  通过服务化架构，把代码模块关系和部署关系进行分离，每个接口可以部署不同数量的实例。

##### mesh 化架构模式

把中间框架从业务进程是分离，让中间件 sdk 与业务代码进一步解耦，从而使中间件升级对业务进程没有影响，甚至迁移到另外一个平台的中间件也对业务透明。

##### serverless 模式

当业务流量到来（业务事件发生）时，云会启动或调度一个已启动的业务进程进行处理，处理完成后云自动会关闭（调度业务进程），等待下一次触发，也就是把应用的整个运行都委托给云。
不适合情况：

- 应用有状态
- 长时间后台运行的密集型计算任务的应用
- 应用涉及频繁的外部 i/o
  适合情况
- 事件驱动的数据计算任务
- 计算时间短的请求、响应应用
- 没有复杂互相调用的长周期任务

##### 存储计算分离模式

分布式环境中 cap 困难主要是针对有状态应用。
c 一致性
a 可用性
p 分区容错性
在云环境中，推荐把各类暂态数据、结构化、非结构化持久数据把采用云服务来保存，从而实现存储计算分离。

##### 分布式事务模式

- 传统采用 XA 模式，虽然具备很强的一致性，但是性能差。
- 基于消息的最终一致性 BASE 通常有很高的性能，但是通用性有限。
- TCC 模式完全由由应用层来控制事务，事务隔离性可控，也可以做到比较高效；但是对业务侵入性非常强，设计开发维护等成本很高。
- SAGA 模式与 TCC 模式的优缺点类似但没有 try 这个阶段，而是每个正向事务都对应一个补偿事务，也是开发维护成本高。
- 开源项目 SEATA 的 AT 模式非常高性能且无代码开发工作量，且可以自动执行回滚操作，同时也存在一些使用场景限制。

##### 事件驱动架构 event driven architecture EDA

本质是一种应用、组件间的集成架构模式。
事件驱动不仅用于（微）服务解耦，还可用于：

- 增强服务韧性
  - 服务间是异步集成的。下游服务器的运行状态不影响上游服务器。
- command query responsibility segregation CQRS
  - 把对服务状态有影响的命令用事件来发起。
  - 对服务状态无影响的命令用同步调用的 api 接口。
  - 可以用于维护数据变更的一致性。
- 数据变化通知
- 构建开放式接口
- 事件流处理
  在 iot 时代大量传感器产生的数据，不会像人机交互一样需要等待处理结果的返回，天然适合用 eda 来构建数据处理应用。

### SOA 的作用

SOA 凭借其松耦合的特性，使得企业可以按照模块化的方式来添加新服务或更新现有服务，以解决新的业务需要，提供选择从而可以通过不同的渠道提供服务，并可以把企业现有的或已有的应用作用为服务，从而保护了现有的 it 基础建设投资。

1. 把应用和资源转换成服务

   SOA 不仅仅是一种技术，也是一种软件架构。企业的决策者只需要根据企业的策略来制定流程，把应用作为服务“拿来就用”，而无需考虑底层的集成。这样可以实现 it 和企业业务之间同步。

### SOA 的设计模式

#### 服务注册表模式

- 服务注册，向注册表公布他们的功能。
- 服务位置，用于查询注册服务，寻找符合自身要求的服务。
- 服务绑定，开发的代码与注册的服务绑定、调用注册的服务以及它们实现互动。

#### 企业服务总线模式

像微核模式
对于点对点的集成方式存在复杂度高、可管理性差、复用度差、系统脆弱等问题。企业服务总线 Enterprise Service bus esb 在此背景下产生了。
功能：

- 提供一种标准的软件底层架构，各种程序组件能够以服务单元的方式“插入”到该平台上运行。
- 组件之间以标准的消息通信方式进行交互。
- 提供位置透明性的消息路由和寻址服务
- 提供服务注册和命名的管理功能
- 支持多种消息传递范型（请求/响应，发布/订阅）
- 支持多种可以广泛使用的传输协议
- 支持多种数据格式及其相互转换
- 提供日志和监控功能。
  本质是中间件形式支持服务单元之间进行交互的软件平台。
  交互过程：

1. 由服务请求者发出一具满足 ESB 要求的请求。
2. esb 根据消息中的服务名或者接口名进行目的组件查找，将消息转发给目的组件。
3. 将处理结构逆向发给服务请求者。
   作用：

- 解耦组件之间的依赖关系，降低软件系统互联复杂性。
- 连接在总线上的组件无需了解其他组件和应用系统的位置及交互协议。只需要向服务总线发请求。
  收益：
- esb 使得企业内部以及外部系统之间可以很容易地进行异步或同步交互
- 采用面向服务的架构为系统提供了易扩展性和灵活性，在提高集成应用的开发效率的同时降低了成本。
- esb 技术克服了传统应用集成技术的缺陷，能够对各种技术和应用系统提供支持。具有灵活性和可扩展性。

按业务领域将服务进行拆分，每个服务独立进行开发、管理、迭代。彼此之间使用统一接口进行交流。实现了分散组件中的部署、管理、服务功能。

```
    |---------------|      |---------------------------|
    | 展示层         |      |       展示层               |
    | 展示层         |      |         |                 |
    | 展示层         |      |  |------+-----------|     |
    |---------------|      | 服务    服务        服务    |
          |                |  |      |           |     |
          |                |  V      V           V     |
          V                | 数据库  数据库       数据库  |
        数据库              |---------------------------|
    单体应用架构                   微服务架构
```

- 复杂应用解耦
- 独立
- 技术造型灵活
- 容错
  - 各微服务相互独立，故障被隔离在单个服务中，其他微服务可通过重试、平衡退化等机制实现应用层的容错。
- 松耦合、易扩展

##### 微服务架构模式方案

没有固定开发模式。

- 聚合器微服务
  - 调用多个微服务实现系统应用程序所需功能。
- 链式微服务
  - 依次调用若干微服务后返回消息。
  - 调用链不宜过长。
- 数据共享微服务
- 异步消息传递微服务
  - rest 设计模式是同步的，容易造成阻塞，会耗费大量时间。消息队列可以将消息写入一个队列，实现业务逻辑以异步方式运行，从而解决阻塞问题。
  - 常用消息队列有：ActiveMQ/RabbbitMQ/RocketMQ/Kafka

##### 微服务架构面临的问题与挑战

- 微服务架构分布式特点带来了复杂性。需要基于 rpc 或消息实现微服务间的调用和通信。使服务发现和服务调用变困难。
- 微服务架构的分区数据库体系，不同服务拥有不同数据库。
- 微服务可能涉及多个服务，对测试较难完成全覆盖测试。
- 在监控、管理、分发、扩容有巨大挑战。
  取舍
  考虑开发团队规模、业务需求变化、系统用户群体规模等诸多因素。使用微服务主要是为了降低应用程序开发、维护等方面的复杂性，如果系统程序无法再扩展、或数据增长速度过快，整个团队都具备微服务思维，采用微服务架构的收益会大于成本。

### 构建 SOA 架构时应该注意的问题

#### 原有系统架构中的集成需求

注意对原有系统架构中的集成需求进行细致的分析和整理。
面向服务的体系结构本质上来说是一种具有特殊性质的体系结构。具有互操作性和位置透明的组件集成构建并互连而成。基于 SOA 的企业系统架构通常都是在现有系统架构投资的基础上发展起来的。我们不需要彻底重新开发全部的子系统。
当遇到一个十分复杂的企业系统时，先考虑应该如何重用已有的投资，不是替换遗留系统。
分析和评估一个已有系统体系结构的集成需求：

- 应用程序集成的需求
- 终端用户界面集成的需求
- 流程集成的需求
- 已有系统信息集成的需求
  着手设计新的体系结构框架时，必须要全面地考虑所有功能的集成需求。

#### 服务粒度的控制以及无状态服务的设计

构建时需要注意：

- 服务粒度的控制
  - 对于将暴露在整个系统外部的服务推荐使用粗粒度的接口，而对于细粒度的接口常用于企业系统架构的内部。
- 对无状态服务的设计
  - 具体服务应该是独立的、自包含的请求。不依赖其他服务的上下文、状态。

1. 建立服务模型

     - 选择端到端的业务流程进行逐层分解到业活动，对其间涉及的业务活动和业务对象进行变化分析。
   - 业务目标分析法
     - 目标分解为子目标，子目标再分派给相关的服务来实现，得到一棵“目标服务树”，处于叶子节点上的每个服务都能回溯到具体的业务目标。
   - 自底向上分析法
     - 通过建立已有系统所具有的功能模块目录列表，可以方便发现可以在不同系统中重用的功能模块，从而将这些模块封装成服务。

2. 建立业务流程

     - 业务对象是对数据进行检索和处理的组件，是简单的真实世界的软件抽象。
     - 业务对象通常位于中间层或者业务逻辑层。
     - 业务对象的分类：
       - 实体业务对象
       - 过程业务对象
       - 事件业务对象
   - 建立服务接口
     - 设计良好的服务接口可以加速开发计划的执行，并对业务组织的灵活性起到促进作用。
     - 是否有状态：是否保留或使用之前的操作。
     - 最好是无状态
   - 建立业务流程
     - 流程：指定的活动顺序。包含明确的用于提供业务值的输入和输出。

###### 嵌入式操作系统的基本功能

**操作系统内核架构**
内核是操作系统的核心部分，管理系统的各种资源。
内核是应用程序和硬件的一座桥梁。
直接运行在硬件上的最基础的软件实体。
分类：

- 宏内核
  - 管理用户程序和硬件之间的系统资源。
  - 用户服务和内核服务在同一空间中实现。
- 微内核
  - 管理所有系统资源
  - 用户服务和内核服务在不同地址空间中实现。
    **任务管理**
    任务管理是嵌入式操作系统最基本功能之一。这里的任务是嵌入式操作系统调度的最小单位。
    `任务 = 程序 + 执行`
    任务的工作状态：
- 执行态
- 就绪状态
- 阻塞状态

```
  执行状态 -------------------------|
    |     <---------------------|  |
    |                           |  | 调度器选择
    | 进程因等待         调度器选择 |  | 另一个进程
    | 输入阻塞            本进程   |  |
    |                           |  |
    V                           |  V
  阻塞态 ----------------------> 就绪态
  执行状态
```

实时系统是指那些对“时间”有严格要求的计算机系统。
由于嵌入式系统中大部分领域是实时系统，
许多嵌入式操作系统都支持优先级抢占调度算法和时间片轮转调度算法。
在嵌入式强实时系统中，操作系统必须支持执行一组并发实时任务，使所有时间关键任务满足其指定的截止时限。
在实时系统的任务调度中，存在大量的实时调度方法：

- 离线 off-line 和 在线 on-line
  - 按获得调度信息的时机
  - 离线：在运行过程中使用的调度信息在系统运行前确定。
    - 具有确定性。缺乏灵活性。
    - 适用于特征能够预先确定，且不容易发生变化的应用。
  - 在线：在系统运行过程中动态获得。
    - 灵活
- 抢占 preemptive 和 非抢占 non-preemptive
  - 按任务在运行过程中能否被打断的处理情况。
  - 抢占：正在运行的任务可能被其他任务打断。
  - 非抢占：正在运行的任务不能被其他任务打断。
- 静态 static 和 动态 dynamic
  - 按任务优先级确定。
  - 静态：在设计时确定下所有任务的优先级，
    - 适用于能完全把握系统中所有任务及其时间约束。
    - 简单，缺乏灵活性，
    - 不利于系统扩展
  - 动态：在运行过程中确定任务的优先级。 - 灵活 - 消耗更多的系统资源
    实时调度算法：
- 最早截止时间优先算法 Earliest Eeadline First EDF
  - 按任务的截止时间确定任务的优先级。截止时间越早越优先。
  - 总是执行任务队列中第一个任务
- 最低松弛度优先 Least Laxity First LLF
  - 按任务紧急程序确定优先级。
- 单调速率调度算法 Rate Monotonic Scheduling RMS
  - 是一种静态优先级调度算法，是经典的周期性任务调度算法。
  - 任务的周期越短，优先级越高。
  - 单调速率调度可认为是最优的。因为若一组进程不能由此算法调度，则不能由任务其他分配静态优先级的算法调度。
    **存储管理**
    其管理的对象是主存，也称内存。
    主要功能：
- 分配和回收主存空间
- 提高主存利用率
- 扩充主存
- 对主存信息实现有效保护
  目标：
- 地址保护 一个程序不能访问另一个程序的地址空间
- 地址独立 程序并发的地址应与物理主存地址无关
  管理方法：
- 分区存储管理
  - 静态分区
    - 预先把可分配的主存储器空间分割成若干个连续区域。区域可不同大小。
  - 可变分区
    - 按作业的大小划分分区
    - 可以克服固定分区方式中的主存空间的浪费
    - 调度算法：
      - 首次适应算法 按顺序查找未分配的表，找到第一个满足长度要求的空闲区。
      - 最佳适应算法 在空闲区中找满足作业要求的最小分区
      - 最坏适应算法 在空闲区中找最大分区
  - 可重定位分区
    - 在作业的动态运行时装入内存的所有地址都是一个相对地址（即逻辑地址），将相对地址转换为物理地址的工作，被推迟到程序指令要真正执行时进行。
- 分页储管理
  - 将一个进程的逻辑地址空间分成若干个大小相等的片。称为页面或页。
- 分段存储管理
  - 作业的地址空间被分成若干段，每个段定义一组逻辑信息。
- 段页存储管理
  - 先将用户程序分成若干个段，再把每个段分成若干个页，并为每个段赋予一个段名。
- 虚拟存储管理
  - 利用实际内存空间各相对大得多的外部储存器存储空间相结合构成一个远远大于实际内存空间的虚拟存储空间。
  - 功能： - 寻址空间 - 内存映射 - 物理内存分配 - 共享虚拟内存
    **任务间通信**
    为操作系统的应用程序提供多种类型的数据传输、任务同步/异步操作等手段。
    操作系统的任务之间关系：
- 相互独立 仅存在竞争 cpu 的资源，再无其他关联。
- 竞争 竞争 cpu 和其他资源
- 同步 协调彼此运行的步调
- 通信 彼此间传递数据和信息
  操作系统提供的任务间的通信手段：
- 共享内存
  - 最直接、最明显的通信方法
  - 访问共享的数据结构

  - 任务间通信、同步和互斥的最优选择，它提供任务间的最快速通信。

    - 二进制的信号量

    - 的信号量

  - 能够在同一处理器的各个任务间传递任意长度的信息。
- socket 和远程调用
  - 是在应用层和传递层的一个抽象层。
  - 可使不同计算机之间通信。即网络通信。

#### 嵌入式数据库

##### 嵌入式数据库的定义及特点

这种数据库嵌入到了应用程序中，消除了与客户机服务器配置相关的开销。实际上是轻量级的。在运行时，它们需要较少的内存。

- 嵌入式系统必须能够在没有人工干预的情况下，长时间不间断地运行。
- 要具备可预知性，系统的大小和性能必须是可预知的。
- 有底层控制的能力。它决定数据库管理操作的关键。
  特点：
- 嵌入式 可以嵌入到其他的软件中，也可以嵌入到硬件中。
- 实时性 对系统的请求第一时间做出响应。
- 移动性
- 伸缩性 根据需要选择结果。

##### 嵌入式数据库分类

- 按嵌入对象分类
  - 软件嵌入数据库
  - 设备嵌入数据库
  - 内存数据库
- 按系统结构不同分类
  - 嵌入数据库
    - 客户端
    - 通信协议
    - 远程服务器
  - 移动数据库
  - 小型 c/s 结构数据库
- 按数据库存储位置分类
  - 内存方式 Main Memory Database System MMDB
  - 基于文件方式 File Database FDB
  - 基于网络方式 Netware Database NDB
    - 无需解析 SQL 语句
    - 支持更多的 SQL 操作
    - 客户端小、无须支持可剪裁性
    - 有利于代码重用

##### 嵌入式数据库的一般架构

如：SQLlite / Brekeley DB
||数据库服务器|嵌入式数据库||
|-|-|-|-|
||允许非开发人员对数据库进行操作|只允许应用程序对其进行访问和控制||
||将数据与程序分离、便于对数据库访问的控制。|将数据的访问控制完全交给应用程序，由应用程序来控制。||
||需要独立的安装、部署、管理|嵌入式数据通常和应用程序一起发布，不需要单独地部署一个数据库服务器。||
分类：

- 基于内存的数据库系统
  - 如 eXtremeDB 基于对象模型，并直接与应用结合。
- 基于文件的数据库系统
  - 如 SQLite 占用资源少。
    - 接口
    - 编译器
    - 虚拟机
    - 后端
    - 特点：
      - 开源、内嵌式
      - 数据库的服务器与客户端在同一个进程中。
- 基于网络的数据库系统
  - 以远程数据库为存储载体，客户端通过移动网访问服务器上的远程数据库。

##### 嵌入式数据库的主要功能

- 足够高效的数据库存储机制

#### 嵌入式中间件

处于操作系统、网络和数据库之上，应用软件之下。
为上层应用软件提供运行与开发的环境，
不仅要实现互连，还需要实现互操作。
对嵌入式应用屏蔽底层操作系统的异构性，常见功能有网络通信、内存管理和数据处理等。
实际应用中将一组中间件集成在一起，构成一个平台。这些中间件中必须有一个通信中间。
`中间件 = 平台 + 通信`
特点：

- 通用性
- 异构性
- 分布性
- 协议规范性
- 接口标准化
  分类：
- 企业服务总线中间件 Enterprise Service Bus ESB
- 事务处理 Transaction Processing TP
- 分布式计算环境 Distributed Computing Environment 创建运行在不同平台上的分布式应用程序所需的一组技术服务
- 远程过程调用 Remote Procedure Call 客户机向服务器发送关于运行某程序的请求时所需的标准。
- 对象请求代理 Object Request Broker ORB
- 数据库访问中间件 Database Access Middleware
- 消息传递 Message passing
- 基于 xml 的中间件 XML-Based Middleware
  这些中间件是设计模式的完整集合。如代理模式、数据总线模式、中介模式。

#### 实时系统设计方法

被各类具备控制能力的系统所采用。

##### Design Approach for Real-Time System DARTS 开发方法的基本概念

###### 1. DARTS 方法

实时结构化分析和设计方法 Real-time Structure Analysis and Design RTSAD
实时结构化分析 RTSA
RTSAD 是对传统结构化分析和设计方法的补充扩展，专门用于开发实时系统。
RTSA 是自顶向下的实时结构化分析方法，用于系统的需求分析阶段。

###### 2. 任务结构化标准

可以为设计人员将实时系统分解为并发任务的时候提供帮助。

###### 3. 信息隐藏

用于信息数据存储和状态转换表的内容和提示。

###### 4. 任务架构图

RTSAD 设计方法使用任务架构图来显示系统分解为并发任务的过程，以及采用消息、事件和信息隐藏模块形式的任务间接口。

##### DARTS 开发过程

- 用实时结构化分析方法 RTSA 开发系统规范
- 将系统划分为多个并发任务
- 定义任务间接口
- 设计每个任务
- 设计过程的成果

##### DARTS 开发方法的评价

优势

- 强调把系统分解成并发的任务，并提供了确认这些任务的标准。强调并发在并发实时系统的设计中非常重要。
- 提供了详细的定义任务间的接口的指南。
- 强调了用任务架构图 STD 的重要性，这在实时系统的设计中也非常重要。
- 提供了从 RTSA 规格到实时设计的转换，
  不足
- 不能像 nrl/ood 完全做到封装数据存储
- 若 RTSA 没做好，则创建任务很困难。
